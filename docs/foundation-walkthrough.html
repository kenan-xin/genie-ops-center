Review order — highest risk first

  1. server/auth.ts + features/password.ts — the security core. Idle config, the session.create.before pending block, onPasswordReset activation, and the plugin enforcing password strength on every password endpoint (review's #1 critical).
  2. server/authz.ts — getServerAuth is the single accessor used by RSC, tRPC, and (later) /api/chat; returns password-change-required and derives the FR tri-state. Everything trusts it.
  3. server/bootstrap.ts + entrypoint.ts — fresh-deploy path: config-first, advisory-locked migrate, atomic admin seed (one createUser call, no follow-up update).
  4. db/schema.ts + drizzle/0000_init.sql — 12 tables, FK cascades, chat_session_handle.generation. Committed SQL matches a fresh drizzle generate.
  5. Dockerfile + docker-compose.*.yml — confirm prod (app.yml) runs no Postgres; HOSTNAME=0.0.0.0; secrets via env only.
  6. components/ui/ — spot-check confirm.tsx, transfer-list.tsx, select.tsx (fixup edits) and (workspace)/layout.tsx (off-canvas reflow).

Important decisions

DecisionWhy
Password strength via a better-auth plugin, not a wrapperbetter-auth's reset/change endpoints only check length; a hooks.before middleware enforces the shared zod rule before the token is consumed / password hashed.
Atomic bootstrap (role + flag + status in one createUser)The two-step create-then-update could strand a fresh deploy with a non-admin user if the 2nd write failed — and bootstrap never retries once any user exists.
Entrypoint holds one PoolClient for lock+migrate+bootstrapSession advisory locks bind to a backend; migrating on a different pooled connection would let the lock slip and let replicas race the migration.
No tenant/org tableOne deployment per customer — isolation at the deployment level; DATABASE_URL is the only dev→prod change.
Status is derived (banned→disabled, status→pending/active)Avoids dual-write drift between better-auth's enforcement flag and our lifecycle field.
AI Elements ported to Base UI (decided, not yet built)One primitive system, no Radix island; the kit's controls are already RHF-ready.

Gotchas

  • server-only in standalone scripts — the container entrypoint is run with node --conditions react-server, the official way to make server-only resolve to its no-op outside Next's build. (The @better-auth/cli generate step is a one-time authoring op that needs a minimal config without server-only.)
  • next build needs env present — server modules are evaluated for page-data; the Dockerfile passes throwaway placeholders (standalone reads process.env at runtime — secrets aren't baked).
  • Migrations ⇒ drizzle-kit only — never run better-auth's own migrate; auth tables are CLI-generated into auth-schema.ts, then owned by the single drizzle history.
  • TransferList TS 71007 — a benign Next RSC-serializability hint on a client-only onChange; tsc/oxlint/build are clean.
  • lefthook re-stamps the hook on every pnpm install (via prepare) — expected.
